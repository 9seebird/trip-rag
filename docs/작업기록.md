## TourAPI 를 쓰면서 걸린 것들

베이스: `https://apis.data.go.kr/B551011/KorService2`

| 오퍼레이션 | 파라미터 | 메모 |
|---|---|---|
| `areaBasedList2` | `areaCode`, `contentTypeId`, `numOfRows`, `pageNo`, `arrange=C` | 100건씩. `totalCount` 를 같이 준다 |
| `detailCommon2` | **`contentId` 만** | `contentTypeId` 를 넣으면 `INVALID_REQUEST_PARAMETER_ERROR` |
| `detailIntro2` | `contentId` + **`contentTypeId` 필수** | 위와 반대다 |
| `detailInfo2` | `contentId` + `contentTypeId` | `infoname`/`infotext` 쌍. 이용요금·화장실 등 |
| `detailImage2` | `contentId`, `imageYN=Y` | 추가 이미지 |

* 옛 버전의 `defaultYN` / `overviewYN` 플래그는 **거부된다.** KorService2 는 플래그 없이 전부 준다.
* 서비스키는 포털이 Encoding/Decoding 두 벌을 준다. Encoding 키를 그대로 파라미터에 넣으면
  이중 인코딩돼 인증이 깨진다. 코드에서 `%` 가 보이면 되돌려 쓴다.
* 게이트웨이 오류는 응답 껍데기가 다르다 — `OpenAPI_ServiceResponse.cmmMsgHeader`.
  `response.header.resultCode` 만 보면 원인을 못 본다.
* `overview` 에 `<br>`, `homepage` 에 `<a href=...>` 가 섞여 온다. 저장 전에 턴다.
* 개발계정 하루 1,000회. **KST 자정 기준**으로 리셋된다 (DB 가 UTC 라 그냥 세면 오전 9시로 착각).

## 1차 실험 결과 (참고용 — 정답 판정 기준을 바꾸기 전 숫자)

질문 19개, 정답 판정이 느슨했던 버전. **절대값은 신뢰하지 말고 순서만 볼 것.**

| 설정 | recall@5 | MRR@10 | 중앙 응답 |
|---|---:|---:|---:|
| 키워드만 | 0.183 | 0.563 | 19ms |
| 벡터만 | 0.312 | 0.737 | 170ms |
| 벡터+조건필터 | 0.207 | 0.566 | 187ms |
| **벡터+리랭커** | **0.437** | **0.833** | 1,322ms |
| 벡터+조건필터+리랭커 | 0.300 | 0.605 | 931ms |

**읽는 법**

* 리랭커가 가장 크게 올렸다. 설계문서의 예측과 일치한다.
  대신 응답이 **8배 느려진다**(170ms → 1,322ms). 좋아진 만큼 비싸졌다.
* 조건 필터는 점수를 **깎았다.** 화면에서는 분명히 나아졌는데(카약이 사라졌다) 숫자는 반대다.
  이게 평가를 붙여야 하는 이유다. 눈으로만 봤으면 "필터 덕에 좋아졌다"고 쓰고 넘어갔을 것이다.

이후 판정 기준을 엄격하게 바꾸고(질문당 정답 최대 8개), `S@k`(정답이 하나라도 상위 k 에
들어온 비율)를 추가했다. 정답이 k 보다 많으면 recall@k 의 최대값이 눌리기 때문이다.

## 3차 실험 결과 (2일차 — 조건 필터 결함 수정 후)

질문 19개, 판정 기준은 2차와 같다. 바뀐 건 코드뿐(`app/extract.py`, `app/search.py`, `eval/run_eval.py`).

| 설정 | S@5 (2차→3차) | recall@5 | MRR@10 | 중앙 응답 |
|---|---:|---:|---:|---:|
| 키워드만 | 0.737 → 0.737 | 0.233 | 0.490 | 20ms |
| 벡터만 | 0.789 → 0.789 | 0.362 | 0.659 | 196ms |
| 벡터+조건필터 | **0.579 → 0.789** | 0.220 → 0.362 | 0.448 → 0.672 | 192ms |
| 벡터+리랭커 | 0.947 → 1.000 | 0.466 → 0.473 | 0.725 → 0.727 | 977ms |
| 벡터+조건필터+리랭커 | **0.737 → 0.947** | 0.275 → 0.427 | 0.463 → 0.708 | 955ms |

유형별 S@5 — 조건필터: 조건형 0.286 → 0.714, 고유명사 0.000 → 1.000.

**읽는 법**

* 조건 필터가 **점수를 깎던 문제는 사라졌다.** 다만 벡터만보다 좋아지지도 않았다(S@5 동일, MRR·S@3 소폭 상승).
  `pet_allowed`·`baby_ok` 가 아직 비어 있어 그 조건은 사실상 아무것도 거르지 않기 때문이다.
  조건 필터가 **득**이 되는지는 `fetch_intro` 이후에 다시 재야 안다.
* **벡터+리랭커는 코드가 안 바뀌었는데 0.947 → 1.000 으로 움직였다.** 리랭커 API 응답이 매번 조금씩 다르다는 뜻.
  질문 19개라 한 문제가 0.053 이다. **0.05 안팎 차이는 잡음으로 본다.** 응답시간(1,489 → 977ms)도 네트워크 편차.
  → 설정마다 3회 돌려 평균·편차를 내는 옵션이 필요하다.
* `q05 비 올 때 시간 때우기` 는 필터+리랭커에서 0.50 → 0.00. 정답이 `9.81 파크`·`엉또폭포`(비 온 뒤에만 물이 떨어지는 폭포)라
  **'비 = 실내' 규칙 자체가 틀린 경우**다. 규칙을 고칠지(비 올 때 ≠ 실내) 정답을 고칠지 검수 때 정할 것.

해석 규칙: 반려동물은 '없음/불가' → 거짓. 유모차는 '없음' 을 **모름**으로 둔다(대여가 없다고 아이랑 못 가는 곳은 아니다).
결과적으로 '아이랑' 필터가 실제로 빼는 곳은 유모차 '불가' 19곳, '강아지' 필터는 아무것도 안 뺀다.

* 차이 자체는 한 질문 분량이라 크지 않다. 그래도 "명세상 필드가 실제로 비어 있었고, 채워진 값도 조건으로 쓰면 오히려 해가 됐다" 는
  평가 없이는 못 봤을 이야기다.

## 미해결

**1. 조건 필터가 점수를 깎는 이유 — 규명 완료**

2차 실험(`eval/results.md`)에서 원인이 드러났다. 조건 필터의 고유명사형 S@5 가 **0.000** 이었다.

* **부분 문자열 오탐.** `extract.py` 의 아이 동반 규칙 `아이` 가 **`아이스뮤지엄`** 에 걸린다.
  `baby=true` 가 켜지고 `baby_ok` 로 거르는데 그 컬럼이 비어 있어 결과가 0건이 된다.
  q01·q06·q20 이 전부 이 경우다.
* **아직 안 채운 컬럼에 필터를 건다.** `pet_allowed`, `baby_ok` 는 `detailIntro2` 를 받아야
  채워지는데 1일차에 하루 한도 때문에 못 받았다. q03(강아지)이 이 경우.
* **유형 규칙이 과하다.** `체험` 이 레포츠(28)로만 한정돼 q14 에서 아이스뮤지엄(12)이 제외됐다.
* **평가와 실제 동작이 다르다.** 화면(`app/search.py` 의 `run`)은 후보가 마르면 약한 조건부터
  자동으로 푸는데, `run_eval` 은 그 단계를 거치지 않고 필터를 직접 건다.
  그래서 실제보다 불리하게 측정됐다. 평가가 제품과 같은 경로를 타게 고쳐야 한다.

즉 **조건 필터라는 발상이 틀린 게 아니라 구현에 결함이 있었다.**
평가를 붙이지 않았으면 "필터 덕에 카약이 사라졌다" 로 끝났을 문제다.

할 일: 조사 경계를 고려한 매칭으로 바꾸기(`아이` → `아이랑|애기|아기|유아|어린이`),
값이 비어 있는 컬럼에는 필터를 걸지 않기, `run_eval` 이 `run()` 을 타게 하기.

**→ 2일차에 코드 수정 완료. 재평가 결과는 위 '3차 실험 결과'.**
