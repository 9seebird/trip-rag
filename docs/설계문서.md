# 여행 코스 RAG — 설계문서

> "비 오는 날 애기랑 갈 만한 제주 실내" 같은 말로 찾고, 고른 곳 근처로 반나절 코스를 짜주는 서비스.
> 한국관광공사 관광정보(TourAPI) 데이터를 벡터 검색으로 다룹니다.

---

## 1. 이 프로젝트가 포트폴리오로 좋은 이유

**RAG가 왜 필요한지가 화면에서 보입니다.**
"비 오는 날"이라는 말은 어느 관광지 설명에도 안 적혀 있습니다. 키워드 검색으로는 못 찾습니다.
그런데 의미로 찾으면 아쿠아리움·박물관·카페가 걸립니다.
데모에서 키워드 검색 결과와 나란히 보여주면 차이가 한눈에 드러납니다.

**하이브리드 검색을 다루게 됩니다.**
"제주"는 의미로 찾으면 안 되고 조건으로 걸러야 합니다. "실내"도 마찬가지입니다.
의미 검색 + SQL 조건 + 좌표 거리를 섞는 구조인데, 실무 RAG는 대부분 이 모양입니다.
"벡터 DB에 넣고 top-k 뽑았습니다"에서 한 단계 위입니다.

**평가가 가능합니다.**
질문을 만들고 정답을 정할 수 있는 도메인입니다. 이게 대부분의 RAG 포트폴리오에 없습니다.

**데이터가 합법입니다.**
공공데이터포털 정식 API입니다. 크롤링이 아니라 공개 배포에 문제가 없습니다.

---

## 2. 범위

- **지역**: 제주 (areaCode 39). 완성 후 부산·강원으로 확장
- **유형**: 관광지 · 문화시설 · 축제공연행사 · 레포츠 · 음식점 (숙박·쇼핑은 2차)
- **예상 건수**: 3,000~6,000건
- **기능**: 상황 검색 + 코스 짜기

---

## 3. 데이터

### 3-1. 어디서 받나

공공데이터포털 → "한국관광공사 국문 관광정보 서비스" 활용신청.
개발계정은 자동 승인, **하루 1,000회** 호출 제한.

### 3-2. 무엇을 받나

| 쓰는 곳 | 받는 것 |
|---|---|
| 목록 | contentid, 제목, 주소, 좌표(mapx/mapy), 대표이미지, 분류코드, contenttypeid |
| 상세(공통) | **overview** ← 임베딩할 소개글. 이 프로젝트의 핵심 필드 |
| 상세(소개) | 운영시간, 휴무일, 주차, 애완동물 동반, 유모차 대여 등 |

`contenttypeid` 참고값: 12 관광지 · 14 문화시설 · 15 축제공연행사 · 28 레포츠 · 32 숙박 · 38 쇼핑 · 39 음식점
(키 발급 후 실제 명세에서 한 번 확인할 것. 버전에 따라 오퍼레이션 이름이 다릅니다.)

### 3-3. 수집 전략 — 하루 1,000회 제한 대응

목록은 한 번에 100건씩 받을 수 있어서 몇 번이면 끝납니다.
문제는 **상세 조회가 건당 1회**라는 점입니다. 5,000건이면 5,000회, 즉 5일치입니다.

그래서 수집 스크립트를 이렇게 만듭니다.

- 목록을 먼저 다 받아 `places` 테이블에 넣고 `overview`는 비워 둡니다
- 상세는 `overview IS NULL`인 것만 골라 하루 900건씩 채웁니다
- 매번 어디까지 했는지 DB가 기억하므로, 중간에 끊겨도 다시 돌리면 이어서 합니다
- 실패한 건은 따로 표시해 두고 나중에 재시도합니다

> 이 "이어서 하는 수집기"는 그 자체로 README에 쓸 거리입니다.
> 외부 API 제한을 어떻게 다뤘는지는 실무에서 자주 나오는 이야기입니다.

## 4. DB 설계

PostgreSQL + pgvector. 이미지 하나만 바꾸면 됩니다.

```yaml
# docker-compose.yml
db:
  image: pgvector/pgvector:pg16
```

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE places (
  content_id     BIGINT PRIMARY KEY,       -- TourAPI 고유 ID
  content_type   INT NOT NULL,             -- 12 관광지, 14 문화시설, ...
  title          TEXT NOT NULL,
  addr           TEXT,
  area_code      INT,
  sigungu_code   INT,
  lat            DOUBLE PRECISION,         -- mapy
  lon            DOUBLE PRECISION,         -- mapx
  image_url      TEXT,
  overview       TEXT,                     -- 소개글 (임베딩 대상)
  indoor         BOOLEAN,                  -- 실내 여부 (아래 5-3 참고)
  usetime        TEXT,
  restdate       TEXT,
  parking        TEXT,
  pet_allowed    BOOLEAN,
  fetched_at     TIMESTAMPTZ,
  detail_status  TEXT DEFAULT 'pending'    -- pending | done | failed
);

CREATE TABLE chunks (
  id          BIGSERIAL PRIMARY KEY,
  content_id  BIGINT REFERENCES places(content_id) ON DELETE CASCADE,
  seq         INT,                          -- 한 장소 안에서 몇 번째 조각인지
  text        TEXT NOT NULL,
  embedding   vector(1024)                  -- 아래 9장 참고. dimensions=1024로 축소해 저장
);

CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
CREATE INDEX ON places (area_code, content_type);
CREATE INDEX ON places (lat, lon);
```

> **주의 — pgvector 인덱스 차원 제한**
> `vector` 타입은 16,000차원까지 저장되지만 **HNSW 인덱스는 2,000차원까지만** 지원합니다.
> qwen3-embedding-4b의 기본 2,560차원을 그대로 쓰면 인덱스를 못 겁니다.
> 비즈라우터가 `dimensions` 파라미터를 모든 모델에서 지원하므로 **1,024로 줄여서 받으면** 됩니다.
> 저장 공간도 절반 이하로 줄고 검색 속도도 빨라집니다. 품질 손실은 실험으로 확인하세요.
> (굳이 2,560을 쓰고 싶으면 pgvector 0.7+ 의 `halfvec` 타입이 4,000차원까지 인덱싱됩니다.)

**청킹**: 대부분의 `overview`가 500~1,500자라 장소당 1~3조각이면 충분합니다.
조각 앞에 제목을 붙여 두면 검색 품질이 올라갑니다.

```
[성산일출봉] 성산일출봉은 제주도 동쪽 끝에 위치한...
```

## 5. 검색 설계

### 5-1. 세 가지를 섞는다

| 무엇 | 어떻게 | 예 |
|---|---|---|
| 의미 | 임베딩 유사도 | "조용한", "아이랑", "비 오는 날" |
| 조건 | SQL WHERE | 지역, 유형, 애완동물 동반 |
| 거리 | 좌표 계산 | 코스 짜기, "근처" |

핵심은 **조건을 먼저 걸고 그 안에서 의미 검색**을 한다는 점입니다.
반대로 하면 "제주" 요청에 강원도 관광지가 상위에 올라옵니다.

```sql
SELECT p.content_id, p.title, p.overview,
       c.embedding <=> :query_vec AS distance
FROM chunks c
JOIN places p ON p.content_id = c.content_id
WHERE p.area_code = 39
  AND (:indoor IS NULL OR p.indoor = :indoor)
ORDER BY distance
LIMIT 8;
```

### 5-2. 질문에서 조건을 뽑아내기

"비 오는 날 애기랑 갈 만한 제주 실내"에서 지역·실내 여부를 뽑아야 합니다.
두 가지 방법이 있습니다.

**규칙 기반**: 지역명 사전을 만들어 문자열로 찾기. 빠르고 공짜지만 표현이 조금만 달라도 놓칩니다.

**모델에게 시키기**: 질문을 JSON으로 바꿔 달라고 요청.

```json
{ "area": "제주", "indoor": true, "with": "영유아", "keywords": "실내 놀이 체험" }
```

느리고 비용이 들지만 유연합니다. **둘 다 만들어서 비교하고 그 결과를 README에 쓰면**
그 자체로 좋은 소재가 됩니다. 규칙으로 먼저 잡고 못 잡은 것만 모델에 넘기는 식도 좋습니다.

### 5-3. 리랭킹 — 한 단계 더

비즈라우터가 `/v1/rerank`를 제공하므로 검색 파이프라인을 이렇게 만들 수 있습니다.

```
질문
 └→ 조건 필터 (SQL)        지역·유형·실내
     └→ 벡터 검색 top 30    의미로 후보를 넓게
         └→ 리랭커 top 5    질문과의 관련도로 다시 줄세우기
             └→ 생성
```

임베딩 검색은 "대충 비슷한 것"을 빠르게 찾는 데는 좋지만 순위가 정확하진 않습니다.
리랭커는 질문과 문서를 **같이 읽고** 관련도를 매기기 때문에 훨씬 정확합니다.
느리고 비싸서 전체에는 못 쓰고, 이렇게 후보를 좁힌 다음에 씁니다.

```bash
curl https://api.bizrouter.ai/v1/rerank \
  -H "Authorization: Bearer $BIZROUTER_API_KEY" \
  -d '{"model":"qwen/qwen3-reranker-8b","query":"비 오는 날 아이랑 갈 만한 곳",
       "documents":["...","..."],"top_n":5}'
```

**포트폴리오 관점에서 이게 큽니다.** 대부분의 RAG 포트폴리오는 "벡터 검색 top-k"에서 끝납니다.
리랭커를 붙이고 **붙이기 전후 recall을 비교한 표**가 있으면 수준이 달라 보입니다.
모델을 직접 띄울 필요 없이 API 한 번이라 비용도 작습니다.

### 5-4. `indoor` 같은 값은 어떻게 채우나

TourAPI에 실내/실외 필드는 없습니다. 세 가지 방법이 있습니다.

- 분류코드로 추정 (박물관·미술관·전시관 → 실내)
- `overview`를 모델에게 읽히고 판단시켜 저장 (한 번만 하면 되니 비용 적음)
- 둘을 섞고, 애매한 것은 비워 둠

이건 **원본 데이터에 없는 값을 파생시켜 검색에 쓰는 사례**라 설명하기 좋은 부분입니다.

### 5-5. 코스 짜기

1. 사용자가 고른 장소를 기준점으로 잡습니다
2. 반경 N km 안에서 유형이 다른 곳들을 후보로 뽑습니다 (관광지 → 음식점 → 카페/문화시설)
3. 후보들을 모델에 넘겨 순서와 이유를 만들게 합니다
4. 총 이동 거리와 예상 소요 시간을 계산해 함께 보여 줍니다

거리는 처음엔 직선거리(Haversine)로 충분합니다.
실제 도로 거리가 필요하면 나중에 지도 API를 붙이면 됩니다.

여기서도 원칙은 같습니다. **후보를 고르는 건 코드가 하고, 모델은 순서를 정하고 설명만 씁니다.**
모델에게 "제주 코스 짜줘"라고만 하면 없는 장소를 지어냅니다.

지도는 카카오맵이나 네이버 지도 JavaScript API가 무료 범위에서 충분합니다.

## 7. 평가 — 이 프로젝트의 승부처

### 7-1. 평가 데이터 만들기

질문 40개를 만들고 각각에 대해 "이건 나와야 한다" 싶은 장소 2~5곳을 적습니다.

```yaml
- q: "비 오는 날 아이랑 갈 만한 제주 실내"
  expect: [제주민속촌, 아쿠아플라넷제주, 제주항공우주박물관]
  filters: { area: 39, indoor: true }

- q: "혼자 조용히 걷기 좋은 곳"
  expect: [사려니숲길, 비자림, 절물자연휴양림]
```

직접 만들어도 되고, 모델에게 장소 설명을 주고 "이 장소가 답이 될 만한 질문을 만들어 줘"라고
시켜서 반대 방향으로 만들어도 됩니다. 후자가 빠릅니다.

### 7-2. 무엇을 재나

**recall@k** — 기대한 장소가 상위 k개 안에 들어온 비율. 검색이 틀리면 뒤는 볼 필요가 없습니다.
**MRR** — 정답이 몇 번째로 나왔는지. 1등으로 나오는 것과 8등으로 나오는 건 체감이 다릅니다.
**근거 충실도** — 답에 나온 장소가 실제로 검색된 목록 안에 있는지. 지어냈는지 잡아냅니다.
**응답 시간** — 검색과 생성을 나눠서.

### 7-3. 실험하고 표로 남기기

| 바꾼 것 | recall@5 | MRR | 비고 |
|---|---|---|---|
| 기준 (청크 500자, 벡터만) | 0.62 | 0.41 | |
| 청크 1000자 | 0.71 | 0.48 | 소개글이 짧아 안 자르는 게 나음 |
| 조각 앞에 제목 붙임 | 0.78 | 0.55 | |
| 조건 필터 추가 | 0.85 | 0.67 | 지역 오답이 사라짐 |
| 임베딩 모델 교체 (openai → qwen3-4b) | ? | ? | **한국어 데이터에서 어느 쪽이 나은가** |
| 차원 축소 (2560 → 1024) | ? | ? | 품질 손실 대비 저장·속도 이득 |
| 키워드 검색 섞음 | 0.88 | 0.71 | 고유명사 질문에서 개선 |
| **리랭커 추가 (top30 → top5)** | ? | ? | 보통 여기서 제일 크게 오릅니다 |

특히 **임베딩 모델 비교**와 **리랭커 전후 비교** 두 줄이 값어치가 큽니다.
한국어 데이터로 임베딩 모델을 비교해 본 국내 포트폴리오는 거의 없습니다.
비즈라우터 덕에 코드에서 모델 이름만 바꾸면 되니 실험 비용도 낮습니다.

**이 표 한 장이 이 프로젝트를 다른 RAG 포트폴리오와 갈라놓습니다.**
숫자는 예시이니 실제로 재서 채우세요. 나빠진 실험도 그대로 적으면 더 좋습니다.

## 8. 운영

미르님이 제일 잘하는 영역이고, 다른 지원자들이 제일 약한 영역입니다. 꼭 넣으세요.

- **비용**: 비즈라우터 응답의 `usage.cost` 필드에 **원화 환산 비용**이 바로 옵니다.
  이걸 로그로 쌓아 두면 "인덱싱 총 얼마, 질문당 평균 얼마"를 표로 낼 수 있습니다.
  제주 2,000건 × 평균 500토큰 ≈ 100만 토큰이라 인덱싱은 몇백 원 수준입니다.
  질문당 비용은 임베딩 1회 + 리랭킹 1회 + 생성 1회로 나눠서 재세요.
- **갱신**: 축제 정보는 자주 바뀝니다. 주 1회 수집 스크립트를 돌리고,
  `overview`가 바뀐 것만 다시 임베딩하는 구조로.
- **속도**: 검색 몇 ms, 생성 몇 초인지 나눠서 기록.
- **공개 데모 안전장치**: 포탈에서 하신 것과 같은 방식으로 하루 사용량 제한.

- **임베딩·리랭킹·생성 모두 비즈라우터 하나로 해결됩니다.** 키를 따로 만들 필요가 없습니다.
  - 임베딩: `POST /v1/embeddings` — OpenAI 호환이라 OpenAI SDK·LangChain 그대로 사용
  - 리랭킹: `POST /v1/rerank` — OpenAI 표준이 아니라 HTTP로 직접 호출
  - 생성: 지금 쓰시는 `google/gemini-3.5-flash-lite`면 충분
  - 인증: `Authorization: Bearer <API Key>`, 베이스 URL `https://api.bizrouter.ai/v1`

| 모델 코드 | 종류 | 기본 차원 | 메모 |
|---|---|---|---|
| `bizrouter/qwen3-embedding-4b` | 임베딩 | 2,560 | 국내 GPU 서빙. 한국어 데이터라 1순위 후보 |
| `openai/text-embedding-3-small` | 임베딩 | 1,536 | 비교 대상. 무난하고 저렴 |
| `qwen/qwen3-embedding-0.6b` | 임베딩 | 1,024 | 가볍고 빠름. 속도 비교용 |
| `qwen/qwen3-reranker-8b` | 리랭킹 | - | 검색 후보 재정렬 |

`dimensions` 파라미터로 출력 차원을 줄일 수 있습니다(모든 모델 지원).
pgvector HNSW 인덱스 한계가 2,000차원이므로 **1,024로 받는 것을 기본으로** 하세요.

> 임베딩 모델을 바꾸면 **기존 벡터를 전부 다시 만들어야 합니다.** 벡터 공간이 달라서 섞어 쓸 수 없습니다.
> 그래서 `chunks` 테이블에 어떤 모델·차원으로 만든 벡터인지 기록해 두면 실험할 때 편합니다.
> 참고로 `bizrouter/qwen3-embedding-4b`와 `qwen/qwen3-embedding-4b`는 같은 모델이라 색인 재사용이 됩니다.
- 화면: 정적 HTML + 지도 API. 라포엠 데모처럼 서버가 직접 서빙
- 배포: Azure 서버, nginx 뒤에 서브도메인
